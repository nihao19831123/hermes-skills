# 战略推演引擎（平台化决策实验）

把"看懂过去"的平台升级为"模拟未来"：用户配置战略参数 → 引擎分年推演 → 输出患者增量/资源压力 → 方案对比 + AI 建议。**必须平台化**：参数入库、结果可查、可对比、数据更新后重跑——用户原话"能支持推演功能，不是现在进行一次推演"。

## 触发场景与用户硬性要求（青岛项目 2026-09，勿违背）
- 用户说"按照《推演方案》设计/改造""支持推演功能""战略变量控制台""A/B/C 方案比较""医院资源容量模型"
- **硬性范围**（用户明确）：① 推演时间范围 1-5 年可选（前端按钮组）② 颗粒度到街道（引擎全 134 街道计算，控制台按区县点选街道）③ **不是一次性脚本**——配置/结果/建议全部持久化，历史可重跑 ④ 号源等运营数据手动刷新入库即可，不挂定时
- 文档驱动：按《推演方案初版》类文档实现"必做 4 项"（推演引擎/A·B·C 对比/资源容量模型/AI 战略建议），"不做"项（复杂预测、Agent 仿真、更炫地图）不加
- **⚠️ 范围变更（2026-09-19，用户明确）："智能体推演"从"不做"升级为本次答辩主线（用户原话"是本次答辩的主线，本身是要突出智能，这是重头"）**。此前按《推演方案初版》"不做 Agent 仿真"拒掉这类需求的判断已过时——再遇到"能不能做智能体推演/人的模拟"要按新增章节与 `references/2026-09-agent-simulation-design.md` 推进，而不是引用旧文档的"不做"清单

## 架构（backend/strategy_engine/ + hospital.db）
```
strategy_engine/
  capacity_profile.py   # 一次性导入: 医生脱敏表聚合 + 号源JSON + 医院参数 → SQLite
  engine.py             # 纯函数 simulate(params) → 分年结果 (无状态可重复调)
hospital.db             # dept_capacity / hospital_params / strategy_config / strategy_result
app.py                  # /api/strategy/run|compare|list|{id}|delete + /api/hospital/capacity
```
- 医生表（350 人/49 科）按科室聚合 doctors/chief/assoc/attending；号源表（92 门诊科）周号源；两表按"科室名映射"合并（医生"心内一科+心内二科"→ 号源"心内科门诊"，映射表 MANUAL_MAP 处理名称不一致；**顶层科室≠可约科室**，号源 children 子科室才是门诊）
- SQLite 4 表：科室画像 / 医院参数 / 推演配置(params JSON) / 推演结果(result+ai_advice JSON)，config_id 关联
- 画像更新（号源刷新/参数变更）→ 重跑即可，无需改引擎
- **⚠️ 严禁重跑 capacity_profile.py build() 更新画像**：build() 开头 `os.remove(DB)` 整库删除重建，会连带清空 strategy_config/strategy_result 全部推演历史，且用户对删库删表零容忍（青岛项目实测 2026-09：任务书里明确"绝不删除/重建 hospital.db"）。正确做法：新增表一律 `CREATE TABLE IF NOT EXISTS`（幂等，app.py 模块加载时执行即可）；要改基线参数用 `INSERT OR REPLACE INTO hospital_params` 单行更新

## 容量与基线模型（真实数据校准）
- **基线锚定真实总量**：街道级模拟分布只取"比例"，归一化到医院真实规模（三医：门诊 55 万、住院 2.6 万）→ `street_opd = 模拟_opd/Σ模拟 × 550000`
- 床位等效容量**反推不假设床位数**：`ipd_capacity = annual_ipd / bed_usage_rate`（26000/0.64≈40625）→ 床位使用率(y) = (26000+Δ累计)/容量
- 门诊供给上限 = 真实周号源×52；号源利用率基线 ≈ 门诊/供给（三医约 77%）
- 距离衰减：15km 内 1.0，更远 `max(0.25, 15/d)`（街道中心到本院 haversine/度近似）

## 三类动作（街道级）
- **specialty 专科提升**：Δ = 街道患者 × 科室占比(dept_share) × magnitude × decay（选"全院"时 dep_w=1）；住院增量 = 门诊×0.8
- **alliance 医联体**：激活低覆盖街道潜在需求 = 人口 × (基准就诊率 − 现状率×0.6 缺口) × magnitude × decay ×0.6
- **capacity 资源扩容**：释放被压制需求，抑制系数 = max(0, (利用率−0.8)/0.2)
- magnitude 限制 0.05-0.5，years 1-5

## 关键数学坑：累进释放别把累计翻倍
错误：`add(i) = 满额 × (i+1)/years` → 末年年增=满额、**累计=2×满额**（第 3 年 1.16万+0.58万… 累计 2.3万 vs 满额 1.17万）
正确：`tri = years(years+1)/2; add(i) = 满额 × (i+1)/tri` → 末年年增=满额×years/tri、累计恰好=满额。街道级展示也乘 `years/tri`。

## API 形态
- POST /api/strategy/run：simulate + 规则 AI 建议(先模板后接 DeepSeek) + 入库，返回 result（含 config_id）
- POST /api/strategy/compare {scenarios:[{name, params}]}：三方案并跑返回对比卡数据（不入库）
- GET list（历史+summary）、GET/{id}（全文）、DELETE/{id}
- AI 战略建议（2026-09 已推进到 DeepSeek 版）：规则模板仍是兜底（按动作类型拼受益区域/资源判断/风险，source:'rule'）；`strategy_advisor.py` 提供 `advise_single(result)`（单方案管理结论：量化概述/资源压力/风险/落地建议，200字内）与 `advise_compare(items)`（多方案比较 + 最优推荐及理由，250字内），调用方式照抄 `ai_explainer.py`：key 只从环境变量 DEEPSEEK_API_KEY 或 `~/.hermes/.env` 读、urllib.request 调 api.deepseek.com、失败自动回退规则模板、返回 `{"text","source":"deepseek"|"rule"}`
- compare 接口返回顶层 `recommendation: {winner, reasons, source}`（AI 生成或规则选出"资源压力可控且新增患者最多"）；ai_strategy_advice 独立表（config_id/scenario/advice_type/content/source/created_at）幂等建表并随 run 落库

## 前端排错（本类项目踩过）
- **HTML id 与 JS id 不一致 → 静默半初始化**：按钮/选项都渲染了但 onclick 全 null（如 HTML `strategyClose` vs JS `stratClose`），报 `Cannot set properties of null (setting 'onclick')`。init 包 try-catch 并 `window.__stratErr=e.message` 暴露，console 一次查清；actGroup/yearSel 有子元素≠初始化完成（绑定在后半段）
- 验证时页面偶发 about:blank / 旧缓存：确认 `location.href` 与 `document.querySelectorAll('[id]').length`，重导航 `?x=N` 绕缓存
- 引擎结果抽查：`simulate({action:'specialty',dept:'心内科',magnitude:0.2,years:3})` 末年年增≈满额×3/6、累计=满额；床位率 = 64%+Δ/容量

## 智能体推演（ABM）扩展（2026-09-19 设计 V1.3 定稿 + 蜂群原型 v0.7 跑通 + **阶段 1 引擎 agent_sim.py 已交付、自检 9/9**）

用户把"智能体推演"定为答辩主线后，产出了三份文档（Windows Documents 与 `/root/agent-sim-design/` 同名）：《智能体推演方案-评审与建议.md》（选型）、《智能体推演-详细设计.md》（可实现的颗粒度）、《智能体推演-验收标准.md》（37 条判据 + 8 条红线）。要点与判据见 `references/2026-09-agent-simulation-design.md`。几条必须记住的结论：

- **选型结论**：MatrAIx（哈佛/MIT，arXiv 2608.04205）是**产品评估基础设施**（用 LLM persona 模拟用户评 AI 产品），不是决策仿真引擎；**只借鉴方法论**（多维人设抽样 → 个体决策 → 群体聚合 → 回测校验），**不照搬工程**（Docker/uv/Node/外网模型 key 与院内内网冲突，且 LLM 决策不可复现）。8.3 亿是**人设库记录数**，不是一次运行的智能体数量——这句最容易被说错。事实清单见 references 同名文件 §事实。
- **主线叙事靠"三层智能"**：L1 个体智能（异质属性 + 效用决策）/ L2 群体涌现（份额转移、瓶颈时点、空间迁移——老引擎给不出的）/ L3 决策智能（**反解目标参数 + 自动寻优**，这是"突出智能"最值钱且原方案缺的一层）。
- **不能用大模型当决策主体**：内网断网即失效、随机不可复现、成本不可控、答不出"这个患者为什么选我们"。LLM 只做语言组织（沿用 ai_explainer/ai_advisor 的既有纪律），无 key 走规则模板。
- **年龄维度已取消**：七普只有街道人口总量，街道级与区级年龄结构都拿不到（实测确认，平台不引入来源不明数据）。异质性改由 5 个数据可得维度承担：专科偏好(dept_share)、忠诚度(HRI 归一化)、就诊倾向(门诊÷人口)、**距离敏感度**、**竞争敏感度(CPI)**——后两个是个体差异化的关键。
- **动工前必须守住**：老引擎 `engine.py`/`app.py` 一行不改（用"基线输出 SHA256 不变"验收）、只新增表（禁 DROP/ALTER、禁 `capacity_profile.build()`）、零新增依赖（纯标准库）、不出现"GPU/算力/本地大模型"表述（用户红线，曾要求连视频画面一起删）。
- **用户要求"看得见的智能"——蜂群可视化是主线展示面，不是后台出数**（原话："要有图形化的页面展示出一个一个的样本的选择，不是后台跑数据……前端蜂群状展示对评委更直观"）。已升格为详细设计第七章 + 验收标准第七节（阶段 6，12 条判据）。三视图：V1 地图蜂群（点落街道、三色态：青绿=选我院/橙=竞争/灰=未就诊）／V2 抽象蜂群（按 距离敏感度×忠诚度 铺开，看异质性）／V3 迁移流（三列＋流带，看份额转移）；再配 **D1 个体详情卡**（点开一个点 → 画像 + 决策理由分量条 + 当年概率）。**D1 数值必须来自后端单点接口，"个体详情与群体结果零误差"是一票否决项**（前端自算 = 废）。
- **v0.3「震撼版」才是用户认的视觉方向（v0.2 被否）**：用户否 v0.2 的原话是"看着没有什么震撼感""图形有点小、看着一团、一闪光分不清楚""不能单独放大地图，只能整体放大"。据此定下的四条硬要求：① **别把上万个点撒满全城**（"一团"的根因）——改成三块"人群方阵"（未就诊／竞争医院／选择我院），人群**整块物理迁徙**到新格位并拖尾，才有"活的"观感；② 动画要有叙事：地图视图年份推进时**从三医向外扩散的青绿波前**，波扫到的街道成片点亮（=能力向外辐射）；③ 加**双蜂群对比视图**（上半屏"不做战略"冻结第 1 年／下半屏"做了战略"末期、同尺度并排），答辩一眼看出差别；④ **删掉闪光环**，改成"改变选择的人亮 ~1s 衰减后落位"，并给"显示 全部/1/2/1/4"抽稀 + 点大小三档 + **地图独立滚轮缩放/拖动平移/双击复位**（点大小按 zoom^0.28 自适应，缩放只作用于地图视图）。
- **可读性必须量化给出换算，别只说"看不清"**：每个点可用面积 = 画布面积 ÷ 点数；实测 800×400 画布放 1.2 万点 → 每点仅约 27px² → 点直径必须 ≤4px（必然密）；实机全屏 1920×1080 → 约 173px²/点 → 点直径可到 7px 且仍有 2–3px 间隙。汇报时直接给这张换算表 + 建议"全屏 + 中等点大小"，再补一句"想更疏就用 1/2、1/4 抽稀（界面标注抽样口径，不糊弄评委）"。点阵间距公式：`cell=sqrt(区面积/最大组内人数)*0.92`、`r=clamp(cell*0.45,…)`；**抽稀后 cell 必须按"实际显示人数"重算**，否则只是块变小、不是点变疏。

- **独立评审暴露的缺陷类（2026-09，交付前必查，细节见 `references/2026-09-review-findings-boundary-and-repro-chain.md`）**：

    `actions=["bogus"]` 目前会**静默产出方案**，必须在枚举白名单层拦掉。
  - **复现链锚定**：`data_version` 由业务库 size+mtime 派生 → 派生种子 → 全部数字，所以**任何写业务库的操作**（promote、演示时被点的旧端点）

    并声明"写库即失配"。
  - **冻结基线要连"排除清单"一起记**（hash + 排除字段 + seed + data_version）：本项目基线只存 hash，导致复核者拿"新增两列概率的 trace"
    比旧 hash 报出**误报**；按"剔除附加列 + 归一化 mtime 派生字段"复算即精确匹配。

  **必须记住的四条**：
  - **过滤分支绝不能用 `continue` 跳过**——被跳过的个体在"每年一行"的概率数组里会留下未初始化值（这里是 0），
    与基线相减就得到**方向相反的假结果**。正确做法是让它们**以零强度参与同一条路径**
    （`L_i = 0.0 if 不在选区 else L`，纯函数 `_agent_step(.., L_i)` 在 L=0 时精确返回基线概率），
    增量自然归零、概率不失真、选择保持基线分布。加一条永久断言：选区外增量恒 0 / 科室无负值 / 与总量同向。
  - **加参数校验层时先枚举"同名不同义"的顶层键**：本项目 `/optimize` 的顶层 `years` 是**候选年份数组**，
    引擎的 `years` 是**年限标量** → 新校验层把合法调用拦成 400（我修完校验层自己踩到，靠 stage-4 回归脚本抓到）。
    解法：`_params(req, skip=("years","magnitudes","depts"))` 显式排除。
  - **外部评审的"哈希不可复现"类断言要先问一句**：它是否**剔除了本轮新增的附加字段**？（本项目基线 trace 哈希
    在"剔除新增概率列 + 归一化 data_version"后精确匹配，评审未剔除故判为不可复现 → 那条是误报；
    但同一项里"data_version 漂移使文档数字失配"是真的。）
  - **验收纪律**：任何"未达标"必须写 FAIL（本项目首屏 ≤2s 实际 3.4s，文档只写数字没标 FAIL，被评审判为验收诚信问题）。
    给每个 PASS 配可重跑的脚本（边界校验脚本 37 例、选区专项断言），否则等于没有证据。
- **在用户仓库里跑脚本的零污染纪律**：`export PYTHONDONTWRITEBYTECODE=1`（否则刷新被 git 跟踪的 `__pycache__/*.pyc`，`git status` 里出现一堆 M 吓人）；证明\"没改现有文件\"用三条命令：`git status --porcelain | grep <新文件>`、`find . -newermt '-40 minutes' -type f ! -name '*.pyc'`、`stat -c '%y %n'` 关键源文件（应仍是旧日期）。
