## 第 6 轮：钻取内「科室对比表」（segDrill 选项 `data-v="table"`）
表列：科室（★=本次目标专科）｜个体｜期初构成条｜期末构成条｜变动｜**我院增量**｜**增量贡献%**（带条）；另有合计行 + 表底两行：
- **末年参考行**：`第 N 年（末年）参考：该街道我院 105 → 150 人（+45）` —— 用户停在第 1 年时"期初=期末"整张表全是 0，不加这行会被当成 bug
- **第 1 年提示条**：`⚠ 当前停在第 1 年 → 期初与期末相同，增量必然为 0。点时间轴「2030」或按 ▶ 播放后再看`
- **宽窗才显示来源列**：`const wide = W>=1180` 时每行追加 `转来 X ｜ 激活 Y ｜ 流失 Z`（窄窗放不下会糊），表底同步加列说明
- 点表头切换排序（`S.tableSort = inc|n`）
- **逐科室聚合抽成 `drillRows(si)`**，表格与 `window.__swarm` 自检共用同一份计算 → 避免"画的和算的不一致"

## 第 7 轮：钻取内「份额转移」（`data-v="shift"`）
- **瀑布**：`期初我院 → +从竞争医院转来 → +从不就诊被激活 → −流失到别处 → 期末我院`，每段标占净增 %
- **自洽核对行（答辩最硬的一句）**：`净增 47 人 = 从竞争转来 49 + 被激活 64 − 流失 66（核对 47 ✔ 一致）`
- **全市竞争医院转入 TOP8**：横条 + 医院名 + 等级 + 距离 + 人数
- 归属口径如实标注：`按患者所在街道最近的竞争医院记（原型简化；正式版按个体可选竞争医院集合建模）`——写明口径，答辩才不会被反问住
- 实测（城阳街道／心内科 +30%／推进到 2030）：期初 106 → 期末 153（净增 +47）；转来 49、激活 64、流失 66、留存 40；全市转入合计 864；TOP5 = 城阳区人民医院 96 / 青岛市第八人民医院 91 / 即墨区人民医院 82 / 青大附院西海岸院区 76 / 青岛市海慈医疗集团 72
- 汇报话术：`净增 47 不是天真的净流入——我们同时算出了流失 66：没有这个战略，这个街道其实是净流失的；增量里 49 人是从五家竞争医院转来、64 人原本根本不就诊、被激活了`（每个数字都指向可查机制）

## 模型保真坑：概率饱和会让"强化 X 却让 Y 最受益"
**症状**：`心内科 +30%` 跑出来目标专科不是最大贡献者（城阳街道：骨科 +15 > 心内科 +5），逐科室表与答辩叙事当场矛盾。
**根因**：选择概率 `p` 被 `clamp(...,0,0.95)` 截断 → 近端街道且偏好匹配的智能体早已顶在 0.95，战略再强也提不动（饱和）；非目标科室反而还有余量。
**修法**：给"专科提升"加**激活项**（语义也对：不只让想来的人更坚定，还让以前不来的人开始考虑）：
```js
let p=clamp(a.p0*m,0,0.95);
if(S.action==='alliance') p=clamp(p+L*al*Math.max(wFar,0.15)*0.85*(1-p),0,0.95);
else if(S.action==='specialty'&&match===1) p=clamp(p+L*dS*0.60*(1-p),0,0.95);   // ← 新增
```
**修后自洽的验收数字**：全市逐科室增量 心内科 +139（第一）／神经内科 111／骨科 101／消化内科 74；命中目标专科人群人均净增 **0.098** vs 其他人群 0.041（**2.4 倍**）。
**通用教训**：任何"概率上限 clamp × 乘性加成"的 ABM 都要检查饱和，否则会出现"强化 X、Y 最受益"。**验收至少加一条：目标人群人均净增 > 其他人群人均净增。**

## 补丁与验证踩坑（本次真实发生）
1. **`drawTile` 格高算成 14px**：134 个街道格子塞进 400px 高画布 → `boxH = th-32 < 3` → 点全被裁掉只剩街名（像素统计里"橙=0"是线索）。改为"按变动人数占比排序的 **TOP30 大阵列**"，格内点阵按 `gcols = ceil(sqrt(n*boxW/boxH))` 自适应
2. **抽稀无效**：格子上限按"全部个体"算 → 抽稀后只是块变小、不是点变疏 → 必须按 `i%stride===0` 的**实际显示人数**重算 `maxPer`
3. **补丁 MISS 引发的 ReferenceError**：`const wide=W>=1180` 因缩进（2 空格 vs 4 空格）未命中，另一处却用到了 `wide` → **patch 前先 `print(repr(...))` 看真实缩进，patch 后跑 `node --check`**
4. **行点击偶发失效**：依赖"绘制时写入的命中框数组"`rowHits` → 受重绘时序影响 → 改为**按行高直接算行号** `idx = floor((my - S.listTop)/S.rowH)`，绘制时记录 `S.pageRows / S.listTop / S.rowH`
5. **切视图／切分组／切点大小后必须立即 `draw()`**，否则"绘制时才写入"的状态（rowHits / backHit / 街道构成缓存）短暂为空，点得快就点不到
6. **覆盖层一律画在点阵之后**：地图 mini 构成条先画被点盖住（点覆盖画布约 78% 面积，像素增量仅 244），移到点循环之后 + 深色底衬才可见

## 客观验收手法（本类原型通用，可直接照搬）
- **页内点计数器**：`dot()` 里 `window.__dots++; window.__dotsBy[ch]++` → 断言"某视图绘制点数 == 该集合个体数"（实测 63===63；纯图表视图应为 0）
- **数据一致性断言**：`各街道三态之和 === 全局三态计数`；`fromComp + fromOut − lost === 净增`
- **像素统计**：按颜色阈值数绿/橙/灰像素 → 判断"是否真画出来了"，并能发现"被遮挡"
- **走真实 UI 路径**：`document.querySelector('.bar button[data-v="streets"]').click()`、`cv.dispatchEvent(new MouseEvent('click',{clientX,clientY,bubbles:true}))`；只调内部函数（`S.view=…; draw()`）会漏掉写在事件处理器里的逻辑（本次排序/分页控件显隐就是漏的）
- **语法门禁**：抽出内联 `<script>` 段跑 `node --check`（多次在交付前拦住语法错）
- **浏览器会话偶发 `about:blank` / `window.__swarm` 未就绪**：重导航加 `?v=N` 或再查一次即恢复，**不要据此改代码**
- **长脚本报出的"失败"先怀疑测试自身**：本次"点返回后排序控件未恢复"是假报——脚本跑几十步后 `S.view` 已漂移到 map，控件本就该隐藏。纪律：关键交互在刷新后的干净页面单独复验再定性，并在汇报里如实说明哪次是测试假报
